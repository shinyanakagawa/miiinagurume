## 1. Google Places API（Place Details / Reviews）

### 1.1 料金体系・無料枠

**2025年3月1日に料金モデルが大きく変更されている**（複数の独立した記事・Google公式ブログ抜粋で一致）。

- 旧モデル：プロジェクト単位で**月$200の無料クレジット**が全SKUに共通で適用されていた
- 新モデル（2025年3月以降）：単一の$200クレジットは廃止され、**SKU（API機能カテゴリ）ごとに個別の無料枠（無料コール数）**が設定される方式に変更
  - Essentials SKU：月**10,000件**まで無料
  - Pro SKU：月**5,000件**まで無料
  - Enterprise SKU：月**1,000件**まで無料
  - 無料枠はAPI全体でプールされず、SKUごとに個別管理される

**Place Details APIの料金ティアとreviewsフィールドの位置づけ（重要）**：
Place Details (New) は、リクエストするフィールドの組み合わせによって課金ティアが決まる仕組みになっている。

| ティア | 単価（1,000件あたり） | 含まれる主なフィールド例 |
|------|------------------|----------------------|
| Essentials | 約$5 | 基本情報（id, displayNameなし等の最小フィールド） |
| Pro | 約$17 | displayName, types, addressComponents 等 |
| Enterprise | 約$20 | photos, rating, currentOpeningHours 等 |
| Enterprise + Atmosphere | Enterprise相当 | **reviews, rating, reviewSummary, priceLevel, delivery, dineIn, takeout 等の口コミ・店舗の雰囲気系フィールド** |

複数の独立記事が一致して報告している内容：**`reviews`フィールドはAtmosphereカテゴリに分類され、Enterprise + Atmosphere SKUの課金対象**になる。リクエスト中に複数ティアのフィールドが混在する場合、最も高いティアで課金される（例：Essentials+Atmosphereのフィールドを同時に要求すると、Enterprise料金が適用される）。

- Enterprise SKUの無料枠は月**1,000件**であるため、reviewsを取得するAPI呼び出しもこの無料枠（月1,000件）の範囲内であれば無料。1,000件を超えると$20/1,000件（目安）の課金が発生する
- 1店舗1ページで初回読み込み時に1回Place Detailsを呼ぶだけなら、店舗数が少ない現状（みーなグルメは現状複数店舗運用前のステージ）では無料枠内に収まる可能性が高いが、**サーバーサイドでキャッシュせず毎回API呼び出しする実装やSSR構成では、アクセス数増加に伴い無料枠を超えるリスクがある**

**補足（要確認）**：旧Places API（Legacy）にも$200クレジットが過去言及されていたが、Legacy版は新規プロジェクトでの利用が制限されつつある（一部記事で「Legacy扱いに移行」との言及あり）。新規実装であれば新Places API (New) を前提に検討すべき。

### 1.2 取得可能なレビューの件数・内容

- 公式のPlace Details APIでは、**1リクエストあたり最大5件のレビューしか返らない**仕様が長年変わっていない（StackOverflow等での開発者からの改善要望が2015年から続いているが未対応、複数の独立記事で一致）
- レビュー本文の長さ・ソート順の指定可否について、二次情報からの確実な確認はできなかった（**要確認**：本文の文字数上限や`reviews_sort`パラメータの詳細は公式ドキュメント本文への直接アクセスができず未確認）
- 5件を超えるレビューが必要な場合は、Google Business Profile API（旧Google My Business API、ページネーションで最大50件/ページ取得可）を使う選択肢があるが、**アクセス申請制で承認に数週間（2〜4週間程度との情報あり）かかる**ため、即時利用はできない

### 1.3 利用規約上の表示制約（重要）

WebSearchで確認できた公式ポリシーページ（Places API Policies）の抜粋に基づく：

- **帰属表示（Attribution）が必須**：レビューを表示する際は、レビュー投稿者の属性情報（表示名・Googleマップ上のプロフィールへのリンク・プロフィール写真）を同時に表示する義務がある（`AuthorAttribution`クラスで取得した`displayName`, `uri`, `photoURI`を画面に出す必要がある）
- **キャッシュ・保存の原則禁止**：Places APIのコンテンツ（レビュー・写真等）は、許可された例外を除き事前取得・キャッシュ・保存することが禁止されている
  - 唯一の明確な例外は`place_id`（無期限保存可）
  - レビュー本文・写真等のその他コンテンツについては、規約上「許可される例外でない限りキャッシュ・保存してはならない」とされている。Google Maps Platformの一部APIには「30日間の一時キャッシュ可」という個別規定があるが、これがPlaces APIのレビューデータにも同様に適用されるかどうかは、検索した範囲の二次情報では確証が取れなかった（**要確認：Google Maps Platform Service Specific Terms の原文をGoogle Cloudの法務担当チャネル等で確認する必要がある**。本調査では `cloud.google.com/maps-platform/terms/maps-service-terms` への直接アクセスがプロキシ制約で失敗した）
  - 実務上の含意：「レビューを定期的にDBに保存して使い回す」実装は規約違反になるリスクが高く、**表示の都度API経由で取得する（その場限りの表示）か、ごく短期間のキャッシュに限定する**設計が安全
- **商用利用**：Places APIのコンテンツはGoogleのコンテンツ・商品ポリシーに従う前提で商用サービスでの利用自体は許可されているが、上記の帰属表示義務とキャッシュ制限が前提条件になる

### 1.4 APIキー管理

- APIキーは**Google Cloudの「プロジェクト」単位**で課金・クォータが管理される。1プロジェクトにつき最大300個のAPIキーを発行可能
- 複数店舗（複数HP）を1つのSaaS型サービスで運用する場合、**サービス全体で1プロジェクト・共通のAPIキー（用途別に制限をかけた専用キー）を使う運用が一般的**であり、店舗ごとに別プロジェクトを作る必要はない。ただし全店舗の呼び出し量が同一プロジェクトの無料枠（Enterprise SKUなら月1,000件）に積み上がるため、**店舗数が増えるほど無料枠を消費しやすくなる**点はスケーラビリティ上の重要な制約
- セキュリティ上は、HTTPリファラ制限・API制限をかけた専用キーを使うことがGoogle推奨のベストプラクティス

## 2. 代替手段の比較

### 2.1 Yelp Fusion API（2026年に「Yelp Places API」に改称）

- **日本でのカバレッジ**：Yelpは2016年前後に日本（米国・カナダ以外の地域）でのコミュニティ運営・現地サポートを終了しており、事実上日本市場から撤退している（Web上の複数の解説記事・ブログで一致）。日本語UIのローカライズ不足や、食べログ・ぐるなび・Rettyなど国内競合の強さが要因として挙げられている
- **実用性の結論**：API自体は技術的には稼働しているとみられるが、**日本の飲食店データの登録数・更新頻度は食べログ等と比較して著しく少ないと推測される（未確認・推測）**。みーなグルメが対象とする日本国内（渋谷・恵比寿・中目黒等）の店舗で、Yelp上に十分なレビューが存在する可能性は低い
- **料金（2026年時点）**：無料トライアルは30日間・上限5,000コールまでだが「評価目的のみで商用利用不可」。本番利用は有料プランのみで、Starar/Plus/Enterpriseのプラン制（1,000コールあたり$7.99〜$14.99程度との情報）。**無料の本番運用枠は存在しない**
- **表示要件**：Yelpブランド（ロゴ）の帰属表示が必須。他社の評価データとブレンドした「総合評価」表示は禁止
- **結論**：日本のカバレッジの薄さと有料化により、みーなグルメの方針（無料枠優先・日本国内店舗中心）には適合しない

### 2.2 Google公式の「埋め込みレビューウィジェット」

- Googleは**個別レビュー本文を表示する公式iframeウィジェットを提供していない**。Googleマップの「埋め込みマップ（Embed a Map）」機能はあるが、これは地図ピンの表示のみで、レビュー本文・星評価は表示されない（クリックしてGoogleマップ側に遷移する必要がある）
- 個別レビューを表示したい場合、Googleは公式の埋め込み手段を用意しておらず、サードパーティウィジェット（後述）またはAPI直接利用のいずれかになる

### 2.3 サードパーティの口コミ集約サービス（Elfsight等）

- **Elfsight「Google Reviews」ウィジェット**：無料プランあり。月間ビュー数**200回まで無料**（1アプリ・1ウィジェット・サイト数は無制限）。200回を超えると一時的にアプリが無効化される。有料プランはBasic（月5,000ビュー・$6/月）、Pro（月50,000ビュー・$12/月）、Premium（月150,000ビュー・$24/月）
- 同様の競合サービス（EmbedSocial, Trustindex, Common Ninja, Featurable等）も同種の「無料プラン＋ビュー数課金」モデルが一般的
- これらのサービスはバックエンドでGoogle Places APIを利用しているため、**結局Google Places APIの5件レビュー制限・帰属表示要件は内包されている**。つまり「サードパーティ＝Google API制約を回避できる」わけではない
- **無料枠の制約**：月200ビューは「ウィジェットが読み込まれた回数」であり、みーなグルメが将来複数店舗・アクセス増を想定する場合、すぐに無料枠を超える可能性が高い。1店舗のみの低トラフィックな試験運用であれば検証に使える程度

### 2.4 「Googleマップで全レビューを見る」への外部リンク誘導のみ

- 実装内容：HP上に「Googleマップでレビューを見る」ボタン/リンクを設置し、クリックすると当該店舗のGoogleマップのレビュータブ（または専用のレビュー投稿リンク）に遷移させるのみ
- Googleの「レビューを書いてもらう」ためのリンク生成は、Google Business Profile上の機能やリンク生成ツールを使えば無料で作成できる（公式サポートページで確認）
- **コスト**：完全に$0（APIキー不要、課金リスクゼロ）
- **実装コスト**：最小（店舗のGoogleマップURL/Place IDを1つ保存し、リンクボタンを設置するだけ。既存の「2.2 地図埋め込みiframe」実装と同様の情報（Place IDまたはマップURL）を流用できる）
- **規約リスク**：外部リンクのみであり、レビューコンテンツ自体を自社サーバーに表示・保存しないため、帰属表示義務やキャッシュ制限の対象外。**規約違反リスクが最も低い**
- **デメリット**：実際のレビュー内容がHP内で閲覧できず、訪問者がGoogleマップへ離脱する一手間が発生する（UX上のコンバージョン低下は懸念点だが、未検証・推測）

## 4. 結論：推奨案

**第一段階（今すぐ実装可能・無料枠優先方針に最も合致）**：
**「Googleマップで全レビューを見る」外部リンク誘導**を採用する。

根拠：
1. CEOの経営理念（時間と費用は安定・成長・永続のためにのみ使用する）および「無料枠優先」の方針に対し、唯一コストが恒久的に$0で済む選択肢である。
2. Google Places APIの`reviews`フィールドはEnterprise + Atmosphere SKU扱いとなり、月1,000件の無料枠を店舗数増加に伴って複数店舗で共有消費する設計になるため、将来の店舗数増加（スケーラビリティ）の観点で無料枠超過・課金リスクが他の選択肢より高い。
3. レビューコンテンツを自社サーバー側で表示・保存しないため、Googleの帰属表示義務やキャッシュ期間制限（本調査では原文未確認のため要確認のまま）に抵触するリスクを構造的に回避できる。
4. 実装コストも最小（既存の地図埋め込み実装で既に保持しているであろうPlace ID/Googleマップ URLを流用し、リンクボタンを1つ追加するだけ）であり、WEB制作担当・データ連携担当の負荷が高い現状（ロードマップのチーム体制セクションで両ロールが最多項目数を抱えている）にも適している。

**第二段階（将来、収益が立ち上がり、店主からのニーズが明確になった場合の拡張案）**：
Google Places API (New) のPlace Details + Atmosphereフィールドを直接連携する案を再検討する。月1,000件のEnterprise無料枠は、店舗数が少数（数店舗〜十数店舗程度、かつHP訪問者がそれほど多くない初期段階）であれば収まる可能性があるため、**「店主が編集画面でレビューを更新ボタンを押した時だけAPIを呼ぶ」「キャッシュは短期間（数日〜規約で許容される範囲）に限定し、表示には毎回Googleの帰属表示UIを必ず添える」**という設計にすれば、無料枠内・規約準拠で実現できる可能性がある。ただしこの場合も「キャッシュ可能期間」の規約原文（Google Maps Platform Service Specific Terms）を法務的に確認し、CEO承認を得てから着手すべきである。Yelp・サードパーティウィジェット（Elfsight等）は、日本でのデータカバレッジの薄さ（Yelp）または店舗数増加時の無料枠超過の早さ（Elfsight：月200ビューは小規模サイトでもすぐに到達しうる規模）から、優先度は低いと判断する。

## CEOへの推奨事項

フェーズ2の4.1（レビュー連携）は、現時点では**「Googleマップで全レビューを見る」への外部リンク誘導のみを実装し、API連携は見送る**ことを推奨します。理由は、Google Places APIでレビュー（`reviews`フィールド）を取得する場合は2025年3月の料金改定により「Enterprise + Atmosphere SKU」という最も高い課金ティアに分類され、無料枠は月1,000件と他のSKUより少なく、複数店舗運用への拡大を見据えると早期に無料枠を超過するリスクがあること、加えてGoogleの利用規約上「レビュー表示時の帰属表示義務」と「コンテンツのキャッシュ・保存の原則禁止」という制約があり（キャッシュ可能期間の正確な日数は本調査では一次情報に到達できず未確認）、実装・保守のコストとリスクに対して得られる効果（5件までしか表示できない）が見合わないためです。Yelp・Elfsight等の代替手段も、日本でのデータカバレッジの薄さ（Yelp）や無料枠の小ささ（Elfsight：月200ビュー）から、現状の「無料枠優先・月間収益0円」のステージには適さないと判断しました。

外部リンク誘導であれば実装コストが最小で恒久的にコスト$0、規約リスクもほぼゼロです。将来、HPへのアクセスが増え店主から「実際のレビューをHP内に表示したい」という具体的な要望が一定数集まった段階で、Google Places API (New) を「店主が手動更新ボタンを押した時のみ呼び出し、帰属表示UIを必ず添付する」設計で再検討することを提案します。その際は、Google Maps Platform Service Specific Termsの原文（キャッシュ可能期間）を法務的に確認したうえで、改めてCEO承認を得るプロセスを踏むべきです。
