# グルメHP作成アプリ インフラ移行設計（Cloudflare / Clerk / PostHog）

## 背景・目的

グルメHP作成アプリのSaaS化に向けて、以下3点の技術スタックを導入する。

- **Cloudflare**：ドメイン管理（DNS）と、店舗ごとの公開HPのサブドメインルーティング
- **Clerk**：認証（現在のSupabase Authを置き換え）
- **PostHog**：データ分析（製品分析・アプリ利用状況の可視化、新規導入）

決済（Stripe）とホスティング（Netlify）、DB/Storage（Supabase）は変更しない。

現時点で実ユーザー（顧客のサイトデータ）は存在しない（テストデータのみ、coconala未受注）ため、データ移行は不要。スキーマは作り直しでよい。

## 全体アーキテクチャ

```
[お客様の店舗HP訪問]
   bistro-miina.miiinagurume.com
        ↓ (DNS: ワイルドカード *.miiinagurume.com → Cloudflare Worker)
   Cloudflare Worker（リバースプロキシ）
        ↓ Hostヘッダーから slug 抽出 → fetch
   Netlify: site.html?slug=bistro-miina（既存のまま）
        ↓
   Supabase（DB/Storage、変更なし）

[店舗オーナーの管理画面]
   app.miiinagurume.com → Netlify（dashboard.html / editor.html）
        ↓ 認証                          ↓ 月額課金
      Clerk                    Stripe（既存Checkout/Webhook維持）
        ↓ JWT発行                       ↓ status同期
   Supabase（Clerk JWT検証、RLS適用、sites.subscription_status）

[分析]
   全ページに PostHog snippet → PostHog Cloud（製品分析・ダッシュボード）
```

## 1. 認証層（Clerk移行）

- **SDK**：フレームワークなしの素のHTML/JS構成のため `@clerk/clerk-js`（Vanilla JS版）をCDN経由で読み込む
- **画面**：`index.html` の自前ログイン/新規登録フォームをClerkの `<SignIn>` / `<SignUp>` マウント型コンポーネントに置き換える（Clerk Hosted UIではなく埋め込み型）
- **Supabase連携**：SupabaseのNative Third-Party Auth機能でClerkを連携プロバイダとして登録し、ClerkのJWT（`sub`クレーム）をSupabaseが直接検証できるようにする
- **DBスキーマ変更**（`supabase/schema_app.sql`、実データなしのため作り直し可）：
  - `sites.user_id`：`UUID REFERENCES auth.users(id) ON DELETE CASCADE` → `TEXT`（Clerk user ID格納、FK制約は外す）
  - RLSポリシー：`auth.uid() = user_id` → `auth.jwt()->>'sub' = user_id`
  - Storageポリシーの `auth.uid()::text` も同様に `auth.jwt()->>'sub'` に変更
- **クライアントコード**：`js/supabase-client.js` の `signUp` / `signIn` / `signOut` / `getCurrentUser` をClerkのAPIに置き換え、Supabaseへのリクエスト時はClerkが発行するJWTを `Authorization` ヘッダーに付与する

## 2. ドメイン/ルーティング層（Cloudflare）

- **ドメイン購入・DNS**：Cloudflare Registrarで`miiinagurume.com`を取得し、Cloudflareネームサーバーで一括管理
- **管理画面用**：`app.miiinagurume.com` をCNAMEでNetlifyの管理画面サイトに向ける
- **店舗公開HP用**：`*.miiinagurume.com`（ワイルドカード）をCloudflare Workerにルーティング
  - Worker処理：受信したHostヘッダー（例 `bistro-miina.miiinagurume.com`）の先頭ラベルを`slug`として抜き出し、Netlifyの`https://<netlifyサイト>/site.html?slug=bistro-miina`にfetchしてレスポンスをそのまま透過的に返す
  - 存在しないslugの場合は404相当のページを返す
- **将来拡張**：店舗オーナーが独自ドメインを使いたい場合、同じWorkerに「カスタムドメイン→slug」のマッピング（KVストア等）を追加すれば対応可能（今回のスコープ外）
- **Stripe Webhook / Supabase Edge Functions**：エンドポイントURLはSupabase側ホストのまま変更なし。Cloudflareは関与しない

## 3. 分析層（PostHog）

- **導入方式**：PostHog Cloud（無料枠で開始）
- **計測対象**：アプリ利用状況（製品分析）に絞る
  - `index.html`：サインアップ/ログイン完了イベント
  - `dashboard.html`：サイト新規作成、テーマ選択
  - `editor.html`：編集操作、「公開する」ボタン押下
  - 課金導線：「月額プランを契約する」クリック→Stripe Checkout遷移、Webhook側で`subscription_status=active`になった時点をコンバージョンと見なす
  - 店舗オーナーの`user_id`（Clerk ID）をPostHogの`identify`に紐付け、ユーザー単位の行動を追跡
- **対象外**：店舗の公開HP（`site.html`）の訪問者解析は今回は計測しない（将来、店舗オーナー向け機能として別途検討）
- **導入箇所**：各HTMLに`<script>`でPostHog snippetを追加するのみ（PostHog Cloud利用のためサーバー側の追加実装は不要）

## 変更しないもの

- **決済**：Stripe（`supabase/functions/create-checkout-session`・`stripe-webhook`は維持）
- **ホスティング**：Netlify（既存デプロイフローを維持）
- **DB/Storage**：Supabase（Auth以外は維持）
