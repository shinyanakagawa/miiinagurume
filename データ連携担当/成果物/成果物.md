# データ連携担当 成果物

## 役割定義
みーなグルメのデータ基盤とAPI連携を担う。Supabaseのスキーマ設計・セキュリティポリシー・API関数の実装・保守を通じて、HP生成アプリとサンプルHPが安定稼働する環境を維持する。

---

## 管轄システム

| システム | 内容 |
|---------|------|
| Supabase（DB） | テーブル設計・RLSポリシー管理・データマイグレーション |
| Supabase Storage | 画像アップロード・公開URL管理 |
| API関数（supabase-client.js） | HP生成アプリのフロントエンドとDBをつなぐAPI層の実装・修正 |
| Netlify Functions | サーバーサイド処理（予約通知・メール送信）のデバッグ・保守 |

---

## 現在のDB構造（2026-06-28時点）

| テーブル名 | 主な用途 |
|-----------|---------|
| sites | 生成されたHPのデータ（店名・業種・HTML等）を保存。`notify_email`/`line_admin_user_id`/`turnstile_site_key`は2026-06-28追加（店主の個人連絡先を含む非公開カラム。下記「既知の課題」参照） |
| （Supabase Storage） | 各店舗のアップロード画像を保存・配信 |

---

## RLSポリシー方針

- 公開用データ（sites）は読み取り自由・書き込みは認証済みユーザーのみ
- Storage buckets は公開アクセス可（HP埋め込み用URLを外部から取得できる状態を維持）

## 既知の課題

| 課題 | 詳細 | 優先度 |
|------|------|--------|
| **【要CEO/データ連携担当対応・セキュリティ】notify_email等が他店舗の認証済みユーザーから読み取れる** | `public read published active sites`ポリシー（`schema_app.sql:64-65`）は`status='published' AND subscription_status='active'`の行を「誰でも」（`anon`・`authenticated`の両方）SELECT可能にする行レベルのポリシーだが、RLSは行単位のフィルタであり列単位のアクセス制御は行わない。2026-06-28に`notify_email`/`line_admin_user_id`のREVOKEを適用した際、コメントで「authenticatedロールは店主が自分のサイトを編集するために引き続きSELECT可能」という設計意図が明記されているが、これは誤りで、REVOKEの対象を`anon`のみにした結果、**ログイン済みであれば自分のサイトを1つも持たないユーザーでも、他店舗の`notify_email`・`line_admin_user_id`・`stripe_customer_id`・`stripe_subscription_id`を、公開済み・契約中の任意の店舗IDに対して直接`select()`するだけで読み取れる**（`グルメHP作成アプリ/js/supabase-client.js`の`getSiteNotifySettings(id)`は`.eq('id', id)`のみで所有者チェックをRLSに委ねており、他人のsite idを渡せばそのまま通ってしまう。実際に動くコードパスがあることを確認済み）。**根本原因**：列単位のREVOKEはロール単位でしか効かず、「本人の行だけ列を見せる」という行×列の両条件を1つのテーブル・1ポリシーだけで表現できない。**修正方針（未実装）**：`notify_email`/`line_admin_user_id`/`stripe_customer_id`/`stripe_subscription_id`をREVOKE FROM authenticatedまで拡張した上で、店主本人が自分のサイトの通知設定を読み書きするための`SECURITY DEFINER`関数（`auth.uid() = user_id`を関数内でチェックしてから返す）をRPCとして新設し、`supabase-client.js`の`getSiteNotifySettings`/`updateSiteNotifySettings`をそのRPC呼び出しに置き換える必要がある。**DBマイグレーションとフロントのコード変更を同時にデプロイする必要があり**（順序がずれると一時的に通知設定の読み書きが壊れる）、今回のセッションでは調整済みデプロイができないため見送り、次回対応のタスクとして起票する | **高（セキュリティ・未対応）** |
| **【要デプロイ】billingカラムの自己付与を防ぐトリガーの拡張が未適用** | `supabase/migrations/2026-07-02_04_protect_billing_columns_on_insert.sql`を作成済み（ローカルPostgresで動作確認済み・詳細は上の保守タスクログ参照）。本番のSupabaseプロジェクトに未適用のため、**適用するまでは認証済みユーザーが決済なしで`subscription_status: 'active'`を自己付与できる状態が残っている**。SQL Editorまたは`supabase db push`等で本番へ適用してください | 高（要デプロイ作業） |
| Resendメール通知 | Netlify Functionsログで `results.email` のエラーが発生。メールが届かない。原因として最も可能性が高いのは、送信元に使っている `onboarding@resend.dev`（Resendの未検証アカウント用共有テスト送信元）の仕様上の制約。このアドレスからは**Resendアカウントに登録・検証済みのメールアドレス宛にしか配信できず**、環境変数 `NOTIFY_EMAIL` が店舗ごとに別アドレスを指していると配信失敗する。2026-06-28に該当箇所（9ファイル）へ `console.error` によるログ出力を追加し、今後はNetlify Functionsのサーバーログから失敗理由を追跡できるようにした。最終的な解決には以下のいずれかをユーザー側で対応する必要がある：(1) Resendダッシュボードで検証済みのメールアドレスと環境変数 `NOTIFY_EMAIL` の値が一致しているか確認する、(2) 独自の送信ドメインをResendで検証し、`from` を `onboarding@resend.dev` から自社ドメインのアドレスに変更する | 高 |
| Resendメール通知（マルチテナント化によるリスク増大） | 2026-06-28実装の汎用Function `send-reservation.js` は、店舗ごとに異なる `sites.notify_email`（店主が自由入力したメールアドレス）宛に送信する設計。送信元を `onboarding@resend.dev` のままにしていると、**Resendアカウントに検証登録されていないメールアドレスを持つ店舗が大半を占めることになり、ほぼ全店舗で配信が失敗する可能性が高い。** サンプル4店舗（固定の`NOTIFY_EMAIL`環境変数）の頃より影響範囲が拡大する。本格運用には、みーなグルメの独自ドメイン（例: `notify@miiinagurume.com`）をResendダッシュボードで送信ドメイン検証（DNSにSPF/DKIMレコードを追加）することが前提になる。コード側は失敗時の`console.error`ログ出力強化までで対応済み（実際のドメイン検証はCEO/ユーザー側のDNS設定作業が必要） | 高 |
| PostHog（site.html訪問者解析） | `template-renderer.js`の`renderAnalyticsSnippet()`はAPIキーがプレースホルダ（`YOUR_POSTHOG_API_KEY`）のままで、実際のPostHogプロジェクトが存在しないため現状は計測されない。go-liveには(1) PostHog Cloudで無料プランのアカウント・プロジェクトを作成、(2) Project API Keyを取得、(3) `template-renderer.js`内の`POSTHOG_API_KEY`定数を実値に書き換える、の3手順が必要（詳細は`データ連携担当/参考資料/2026-06-20-posthog-analytics-plan.md`の追加スコープ節） | 中 |
| Cloudflare Worker（サブドメイン自動付与） | `cloudflare-worker/`はコードのみ実装済みで、実際のCloudflareアカウントへのデプロイ・ドメイン購入は未実施。`wrangler.toml`の`account_id`・`NETLIFY_ORIGIN`はプレースホルダのまま。**ドメイン購入は実費が発生するため、デプロイ前にCEO承認が必要**（詳細手順は`cloudflare-worker/README.md`） | 中 |
